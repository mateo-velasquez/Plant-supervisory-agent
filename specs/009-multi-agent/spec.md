# 009 · Multi-agent with a single writer — Spec

- **Status:** Implemented
- **Requirements:** FR-28, FR-29, FR-37, NFR-03
- **Stories:** — (US-08, FR-20 and the injection part of NFR-06 moved to spec 010)
- **Decisions:** ADR-0002, ADR-0003, ADR-0009 (orchestration pattern; created by the main session with `/new-adr` before Ready), ADR-0013, ADR-0014, ADR-0015. Q-01, Q-12, Q-27, Q-38, Q-43, Q-48 (reused); Q-50, Q-51, Q-52, Q-53, Q-54 (decided here); Q-41 (amended by Q-51 and Q-54).
- **Week:** W3

## Goal
Split the snapshot's judgment in two: a read-only **investigator** reads the logbooks and returns typed cause proposals; code validates them; the **coordinator**, the only writer, never sees a raw logbook, applies the proposals it accepts and writes the texts. Gap, shipment and bottleneck perspectives are computed by code. Each agent gets only what changed, and cost is recorded per agent.

## Scope
- **In:** the per-snapshot pipeline (ADR-0009); the investigator (prompt v1, tools, JSON output); proposal types and the code control with one correction round and a safe fallback; the reviewed-logbook registry (schema v4); missing logbooks; `apply_proposal`; coordinator quarantine, brief v3 with code-built perspectives, prompt v3; when each agent is called; per-agent trace and run totals; settings; the capabilities table (FR-28); the days 1–7 run (user-run).
- **Out:** hooks, code-enforced allowlists and the criteria MCP prompt (010: 009 defines the lists, 010 enforces them); the US-08/FR-20 injection examples (010); structured output and caching (011); trend in the gap perspective (016).

## Decisions
- **D1 · Pattern (ADR-0009):** a code-driven pipeline per snapshot, sequential, one pass, no recursion: `decide` (code) → investigator when a readable logbook is not yet reviewed → control (code) with one correction round → coordinator brief (code) → coordinator only when there are texts to write or validated proposals → `finish` (one save). Rejected for the ADR: orchestrator-worker (analysts as coordinator tools) and an LLM fan-out of gap/shipment/bottleneck analysts.
- **D2 · FR-28 (Q-50):** the brief asks only to choose a pattern; FR-28's text stays. Gap, shipment risk and bottleneck are separate perspectives computed by code and put in the coordinator brief. One reader agent (investigator), one writer agent (coordinator).
- **D3 · Quarantine:** the coordinator never reads raw logbooks, not even on fallback. Investigator tools: `list_available_logbooks`, `get_logbook`, `get_case`, `get_delayed_units`; no write tool of any kind.
- **D4 · Applying proposals:** one write tool `apply_proposal(propuesta)`. Code fills category, stage, scope and citation from the validated proposal and calls the 008 writers through `SnapshotJudgment`, so ledger refusals still apply. Declining = not applying; the trace records applied vs declined. `set_cause`, `raise_severity` and `lift_severity_raise` stay in the server with their tests, but no agent's list offers them.
- **D5 · Proposal shape:** `tipo` (`set_cause`, `raise`, `lift`), `categoria`, `etapa`, scope (`case_id`; `modelo` + optional `mercado`; `causa_activa`), `bitacora`, `fragmento`, `estado_causa` (`activa_sin_fecha`, `con_fecha`, `resuelta`). No numbers. Zero proposals is a valid result.
- **D6 · Control:** schema, size cap, `no_declarada` refused, `estado_causa` (`raise` only with `activa_sin_fecha`, `lift` only with `resuelta`), `verify_citation` (Q-01, Q-12). One correction round; a second failure, turn cap, budget, refusal or `max_tokens` → **safe fallback** (no judgment this snapshot). `ModelCallFailed` in the investigator aborts the snapshot resumably (Q-43).
- **D7 · No domain change:** the investigator also receives the cases without a cited cause evaluated at N and may read earlier readable logbooks. A case opened at a mid snapshot gets its cause at the next closing (Q-41 as amended in 008). A mid snapshot alone does not trigger the investigator, except a retry (D8).
- **D8 · Reviewed logbooks (schema v4):** a failed attempt is retried at the next snapshot (possibly a mid one); after the second failed snapshot attempt the logbook is given up (`sin_revisar`) and never retried. Trigger = "a readable logbook neither reviewed nor given up".
- **D9 · Missing logbook (Q-52):** "no result": causes stay `no_declarada`, the trace is marked, the snapshot is not cut, and it counts as a failed attempt: checked again at the next snapshot, `sin_revisar` after the second.
- **D15 · When a review succeeds (Q-53):** a logbook is `revisada` only when the investigator ends with a valid output **and** either it holds no proposals, or the coordinator ran and ended `done`, or the coordinator applied every validated proposal (a later fallback on texts only, e.g. `fallback:missing_texts`, does not undo the review). Validated proposals left unapplied plus a coordinator fallback → failed attempt (`reintento`, same cap). Proposals the coordinator declined while ending `done` count as reviewed. The mark is written after the coordinator step.
- **D16 · Alert without a cause (Q-54, amends Q-41, added after `/verify-criteria`):** a required alert for a case without a cited cause, at a snapshot with no review, triggers one cause-lookup run of the investigator over the readable logbooks (R2b), so §6 holds without exception. Same agent and role; only the trigger is new, in code. No review mark, no attempt.
- **D10 · Coordinator call (Q-51, amends Q-41):** only with a required text or at least one validated proposal; the closing review moves to the investigator.
- **D11 · Delta and perspectives (FR-29):** each agent receives only what changed (R2, R10). The gap perspective is an extension point for spec 016 (trend), not implemented here.
- **D12 · Real run:** the days 1–7 run (008 R22 pending plus 009) is run by the user at the end; no single-agent mode is kept. 007/008 expectations that change are listed in Acceptance (changed, never deleted).
- **D13 · Injection:** the US-08 example and FR-20 tests move to spec 010; 009 keeps only the structural defenses (R12).
- **D14 · Interface choices** (taken by the spec writer, see plan): **I1** investigator output is one JSON object in its final text (a ```` ```json ```` fence is tolerated), validated with pydantic; no structured output, no submit tool. **I2** proposal ids are code-assigned after control, `<snapshot_id>-p<n>` in output order. **I3** a `lift` carries no `categoria`/`etapa` (the active cause has them). **I4** control is all-or-nothing; per proposal the first failing check is reported, every proposal is checked. **I5** control also checks that a scope id belongs to the task. **I6** the size cap counts the raw final text. **I7** validated proposals live in a per-snapshot `ProposalBook` on the frame (memory only); the trace stores them in full. **I8** `apply_proposal` re-verifies the citation like the 008 tools, then calls `CauseWriter`/`RaiseWriter`; no new writer protocol. **I9** one tool server per agent over one shared `FrameHolder`; the investigator's frame carries no writer and no book. **I10** `Coordinator` (the loop class) is reused for the investigator; the loop has **one end-of-turn path**, an `EndReview` (`review(text) -> note | None` plus the outcome when exhausted): the coordinator's missing-texts reminder becomes `MissingTexts` (`fallback:missing_texts`, 007 E8 unchanged), the investigator passes `ProposalReview` (`fallback:invalid_output`); `progress` serves only the early stop after a tool turn. **I11** one `ModelPort` serves both agents; `prompt_token_limit` and `anthropic_max_tokens` apply to every request. **I12** the trace keeps its top-level fields as the coordinator's (`skipped` when it did not run) and adds an `investigator` entry and `agents_run`; `by_agent.runs` counts agents that actually started. **I13** review marks are `revisada`, `reintento`, `sin_revisar`. **I14** perspectives use Spanish keys; floats are rounded inside the builders with `DECIMALS` (1), moved to `domain/numbers.py` and imported by the read views. **I15** a missing logbook is a store refusal `logbook <T> is missing`. **I16** `SnapshotDecision` gains `cited`. **I17** a mutable `ReviewLog` (rejections, accepted) is created by the pipeline next to the `LoopLog`, so an aborted line keeps `control_errors`. **I18** `InvestigatorStep` (plan, run, record) and `CoordinatorStep` in `runner/`; `AgentPipeline.process` only sequences them and picks the reason. **I19** registry migrations are a chain of one step per version.

## Behavior

### R1 · Pipeline per snapshot (ADR-0009, FR-28, ADR-0002)
In `AgentPipeline.process`, inside the snapshot's unit of work:
1. `decide` (code): metrics, lifecycle, notices, as in 008.
2. **Plan:** pending logbooks (R2), split into present and missing (R8). Before the first model request of the snapshot, the 007 R11 unit check runs.
3. **Investigator** (R3) when a pending logbook is present; then **control** (R5, R6). Nothing is written yet.
4. **Reason** (R9). The coordinator runs only for `text_needed` or `proposals`, with the brief of R10, in a frame carrying the snapshot writer and the proposal book.
5. The 008 failure check; then the **review marks** are written (R7, Q-53), knowing the coordinator's outcome; then `finish(writer.final())` once; then the trace line is staged (R14).
Each step runs once; nothing loops back.

### R2 · Investigator trigger and task (FR-29, Q-01, D7, D8)
- **Pending** at N = the shifts `LogbookStore.available(N)` lists (closed at N, not held out) that are neither reviewed nor given up, in calendar order. Today this is the closing snapshot's own logbook; it also covers retries and gaps.
- The investigator runs at N iff at least one pending logbook is present (R8).
- Its task (first user message) is a constant instruction line plus compact JSON: `snapshot_id`, `turno_id`, `posicion`, `bitacoras` (present pending ids), `casos_sin_causa` (cases evaluated at N, the last delta's, with no cited cause: `{case_id, modelo, mercado, estado, etapa}`, `etapa` = Q-32 stage) and `causas_activas` (008 R15 item shape). Nothing else is carried from earlier snapshots.

### R2b · Cause lookup for an alert without a cause (D16, Q-54, §6)
- When the investigator does **not** run a review at N (no present pending logbook), at least one logbook is available at N (`LogbookStore.available`, closed by N; with none there is nothing to read), and at least one required `alerta_inmediata` decision is for a case without a cited cause, the investigator runs once in **cause-lookup** mode: same prompt, tools, loop, control and correction round as R3–R6.
- Task: the R2 shape with `bitacoras` `[]`, `casos_sin_causa` = only those alert cases, and `causas_activas`; the instruction line says to look for each case's cause in the readable logbooks (`list_available_logbooks`, `get_logbook`). Nothing else changes in the agent.
- Control adds one check before 4a: only `set_cause` proposals are accepted in this mode (`only set_cause is proposed when looking up a cause; got <tipo>`). Raises and lifts belong to reviews.
- It writes **no review mark** and counts as no attempt (R7). Any outcome other than `done` → no proposal, the alert keeps `no_declarada` (safe fallback, trace marked). `ModelCallFailed` aborts as in R6.
- Its accepted proposals reach the coordinator as in a review; the coordinator runs anyway (`text_needed`). The early-stop gate of R11 applies.
- In days 1–7 it never runs: every mid-snapshot alert there already has a cause from a raise (Q-48, Q-49).

### R3 · Investigator loop (I1, I10, ADR-0014)
- Fresh conversation per run; `system` = investigator prompt v1; tools = `INVESTIGATOR_TOOLS`; at most `investigator_max_turns` requests; 007 R4–R7 hold (tool errors, append-only history, budget guard, retries).
- Nothing is required, so a `tool_use` turn never ends the loop. Every `end_turn`, for both agents, goes through the loop's single `EndReview` path: the reply's text is reviewed; no note → `done`; the first note is appended as a user turn and the loop continues; a second note ends with the review's exhausted outcome. For the investigator the review is control (R5): note = the R6 correction, exhausted = `fallback:invalid_output`. For the coordinator it is `MissingTexts`: note = the 007 reminder, exhausted = `fallback:missing_texts` (007 R3 unchanged).
- `refusal`, `max_tokens`, unexpected stops, turn cap and budget end as in 007 R3/R6.

### R4 · Proposal schema (D5, I1, I3)
The final text, stripped of one optional ```` ```json ```` … ```` ``` ```` fence, must be `{"propuestas": [...]}`; each item is discriminated by `tipo`, every key required unless stated, unknown keys refused:
- `set_cause`: `case_id`, `categoria`, `etapa`, `bitacora`, `fragmento`, `estado_causa`.
- `raise`: `categoria`, `etapa`, `modelo`, `mercado` (optional, `null` = any market), `bitacora`, `fragmento`, `estado_causa`.
- `lift`: `causa_activa`, `bitacora`, `fragmento`, `estado_causa`.
`categoria` ∈ §6 catalog, `etapa` ∈ production stages, `modelo`/`mercado` ∈ the domain enums, `estado_causa` ∈ {`activa_sin_fecha`, `con_fecha`, `resuelta`}. There is no numeric field.

### R5 · Control (D6, Q-01, Q-12, §5, §6, I4–I6)
`check_output(text, task)` returns either the accepted proposals (ids `<snapshot_id>-p<n>`, n from 1 in output order) or a list of errors, in this order:
1. Raw text longer than `proposal_output_max_chars` → only `output is <n> characters, over the maximum of <max>`.
2. Not one JSON object → only `output is not a JSON object`.
3. Schema errors → one `schema: <location>: <message>` per error (pydantic wording, not pinned).
4. Per proposal, the first failing check, prefixed `propuestas[<i>]: `:
   a. `categoria` `no_declarada` → `no_declarada is never proposed: code keeps it when no logbook names a cause`;
   b. `raise` without `activa_sin_fecha` → `raise needs estado_causa activa_sin_fecha, got <value>`; `lift` without `resuelta` → `lift needs estado_causa resuelta, got <value>`; `set_cause` accepts any value;
   c. scope: `case <id> is not in this task` (`case_id` not in `casos_sin_causa`); `active cause <id> is not in this task` (`causa_activa` not in `causas_activas`);
   d. `LogbookStore.verify_citation(bitacora, fragmento, N)`: its refusal text (`fragment not found in T05`, `logbook T06 is not available at S010: it closes at S012`, `logbook T05 is missing`, …).
Any error rejects the whole output. Control never judges whether a fragment supports the state (X2). Duplicates and conflicts with causes in force are left to the ledger (X3).

### R6 · Correction round and safe fallback (D6, Q-43)
- **Correction:** the first rejected output gets one user turn: `Code rejected your output. Fix these errors and send the whole JSON again:` followed by one `- <error>` line per error.
- **Safe fallback** when the run ends with any outcome other than `done`: no proposal this snapshot, the code floor stands, causes stay `no_declarada` (or whatever the registry holds), the trace is marked, and every task logbook gets a failed attempt (R7). Proposals are never partially kept.
- `ModelCallFailed` (or any other exception) propagates: `RunAborted`, rollback, resumable; no review mark is written. The aborted line keeps the investigator's records, `control_errors` included (I17).

### R7 · Reviewed-logbook registry, schema v4 (D8, D15, Q-52, Q-53, ADR-0003)
- A table `logbook_reviews` holds per logbook `attempts`, `last_attempt_at`, `reviewed_at`, `given_up_at`; rows are written only inside the unit of work, by code, after the coordinator step and before `finish`.
- Every task logbook and every missing pending logbook gets one attempt at N. The attempt **succeeds** iff the logbook was present, the investigator ended `done` (control accepted its output), and either no proposal was accepted, or the coordinator ran and ended `done`, or every accepted proposal was applied (`proposals_declined` empty) before a coordinator fallback (Q-53). Success → `reviewed_at` = N, mark `revisada`. Failure → mark `reintento`, or, when `attempts` reaches `logbook_review_max_attempts` (2), `given_up_at` = N and mark `sin_revisar`.
- So a coordinator fallback (turn cap, budget, refusal, `max_tokens`, unexpected stop, missing texts) after accepted proposals sends the logbook back to the investigator at N+1, with the effects already applied visible in its task (`causas_activas`, cited cases leave `casos_sin_causa`).
- `SCHEMA_VERSION` 4. Migrations are a chain of one step per version (v2→v3 frozen from 008, v3→v4); a file found at version v runs every step from v, then sets 4, in one transaction. A fresh file = frozen v2 body + every step, so fresh and migrated files have the same `sqlite_master`. A failure rolls back and re-raises; the file keeps its version. Any other version raises `ValueError` naming the file, the version found and 4.

### R8 · Missing logbook (D9, Q-52)
- **Missing** = a pending shift whose file `<turno_id>.txt` is not in `logbooks_dir`. `LogbookStore.get` (and so `get_logbook` and `verify_citation`) refuses it with `logbook <T> is missing` (a `RejectedRequest`), never `DataLoadError`.
- A missing logbook is not put in the task; with no present pending logbook the investigator is not called. Causes stay `no_declarada`; the snapshot commits; the investigator trace entry lists it in `missing`.
- It gets a failed attempt (R7): checked again at the next snapshot, `sin_revisar` after the second.
- An empty file is present, not missing (X7).

### R9 · When each agent is called (Q-51, amends Q-41)
- Before the investigator: `text_needed` if the draft has a required text, else `investigator_only` if a pending logbook is present, else `no_text_needed`.
- After control: a non-`text_needed` reason becomes `proposals` when at least one proposal was accepted.
- The coordinator runs iff the reason is `text_needed` or `proposals`. `decision` is `call` iff any agent sent a request or was due to (`text_needed`, `proposals`, `investigator_only`), else `skip`.
- `closing_review` is no longer written; old trace files with it still parse. A closing with no news and no proposals calls only the investigator; a mid snapshot with no text and no pending logbook calls nobody.
- Aborted lines carry the reason taken so far (the pre-investigator reason when the investigator aborts).

### R10 · Coordinator brief v3 and perspectives (FR-29, D2, D11, I14)
- The brief is the 008 instruction line (new text) and JSON with `snapshot_id`, `turno_id`, `posicion`, `alertas`, `novedades`, `causas_activas` (unchanged), plus `perspectivas`; then, only when proposals were accepted, a block `<propuestas snapshot_id="N">`, one compact JSON per line (`{"id", …R4 keys}`), `</propuestas>`. Inside the block `<propuestas` and `</propuestas` (any case) are escaped as `&lt;…`, as `render_logbook` does.
- `perspectivas`: one item per case of the **required** notices at decide time (alerts first, then news, each case once): `{case_id, gap, embarque, cuello}`.
  - `gap`: `unidades` and `pct_plan_diario` at N (combination metrics), and `en_ultimo_informe`: `{snapshot_id, unidades, pct_plan_diario}` from the case's history row at `last_reported_at`, or `null` if never reported.
  - `embarque`: `unidades_demoradas` (FR-10 count), `retraso_dias` (combination delay at N), and `embarque_asignado`/`embarque_alcanzable` of the unit that sets that delay (eligible units, `None` delay first, then largest, ties by `unidad_id`); both `null` with no eligible unit.
  - `cuello`: `{etapa}` = the combination's bottleneck at N.
- Each perspective is built by a pure builder (the gap one from the case, its combination metrics at N and its stored history), which rounds floats to `DECIMALS` (1).
- **016 extension point = the brief shape:** spec 016 adds a `tendencia` field to `perspectivas[].gap` (it may also use the investigator's `estado_causa`); the rest of the item stays as here. The builder's signature may change in 016.
- Numbers come only from code; the model never computes them.

### R11 · `apply_proposal(propuesta)` (D4, I7, I8, Q-27)
Checks in order, the first failure is a refusal:
1. the frame has a proposal book and a judgment writer, else `no proposals are being applied at this snapshot`;
2. the id is in the book, else `unknown proposal <id> at <snapshot>`;
3. it is not applied yet, else `proposal <id> is already applied`;
4. the citation verifies at the frame's snapshot (008 `_cited`);
5. the 008 writer call: `set_cause(case_id, Cause, Evidence)`, `raise_severity(categoria, CauseScope, Evidence)` or `lift(causa_activa, Evidence)`; ledger refusals (e.g. `active cause … already covers …`) propagate unchanged.
On success the id is marked applied, and the result is `{"propuesta": <id>}` plus the 008 keys of that judgment (`caso`/`causa`, `causa_activa`/`casos`, `causa_activa`/`levantada_en`), `avisos`, `pendientes`. Re-decide, rebase and the 008 R10 failure guard are unchanged. The coordinator cannot pass category, stage, scope or citation.
- **No early stop over unapplied proposals (Q-53, added after review):** the coordinator loop's early stop after a tool turn (007 R3.1) does not fire while the book holds an unapplied proposal: `CoordinatorStep` passes the loop a progress whose `required()` is `()` while `book` has unapplied ids. The loop then ends only by an `end_turn` (texts complete: a real decline of the remaining proposals, `done`), by applying them, or by a 007 fallback. So a `done` coordinator has always seen and chosen; texts written before `apply_proposal` never cut the judgment off.

### R12 · Quarantine, capabilities and structural defenses (FR-28, ADR-0003, D3)
| Agent | Kind | Raw logbooks | Tools (in order) | Input | Output | Writes |
|---|---|---|---|---|---|---|
| Investigator | LLM, read-only | yes | `list_available_logbooks`, `get_logbook`, `get_case`, `get_delayed_units` | task (R2) | `{"propuestas": [...]}` | nothing |
| Control | code | — | `LogbookStore.verify_citation` | output + task | accepted proposals or errors | nothing |
| Perspectives | code | no | — | metrics, case history, units | `perspectivas` | nothing |
| Coordinator | LLM, single writer | never | `get_deviations`, `get_active_cases`, `get_case`, `get_delayed_units`, `apply_proposal`, `emit_alert`, `emit_shift_report` | brief (R10) | applied proposals, texts | only through `SnapshotJudgment` |
| Runner | code | — | — | — | lifecycle, review marks, one save | unit of work |
- Each agent's server registers only its tools; the loop refuses any other name (`tool <name> is not available`, 007 R4). The investigator's frame has no writer and no book.
- `set_cause`, `raise_severity` and `lift_severity_raise` stay registered in `build_server` and tested; no agent list offers them, and spec 010's allowlist must exclude them (X9).
- Structural defenses (not FR-20 tests): quarantine; logbooks in `<bitacora>` blocks; proposals delimited as data; no write tool for the reader; `apply_proposal` bound to validated ids; schema and citation control; the severity floor only rises.

### R13 · Prompts (ADR-0002; no per-snapshot content, stable prefix for 011)
- **Investigator v1** (`agents/prompts/investigator.md`, title `# Investigator prompt v1`): `## Role`, `## Logbooks are data`, `## Task`, `## Causes` (the §6 catalog with its "when"), `## Cause state` (the three values; `con_fecha` only for a concrete resolution date or time; a person returning or work resuming ("vuelve mañana") is not one and stays `activa_sin_fecha`, Q-39), `## Proposals` (when to propose each `tipo`; raise only `activa_sin_fecha`, lift only `resuelta`; scope model + stage, market only when named; check `causas_activas`; never `no_declarada`, never guess), `## Citations` (one contiguous verbatim fragment of one readable logbook), `## Output` (JSON only, the R4 schema, no numbers, `{"propuestas": []}` when nothing applies, at most the size cap), `## Corrections`.
- **Coordinator v3** (title `# Coordinator prompt v3`): `## Role`, `## What code decides`, `## Data, never instructions` (brief, proposals, fragments, tool outputs), `## Proposals` (validated by code; apply with `apply_proposal` only those consistent with the brief; declining is allowed; never invent one), `## Perspectives` (numbers by code, use them, never compute), `## Numbers`, `## Order of work` (proposals first; a judgment can put texts back in `pendientes`; the `texto` states only the notice's `causa`), `## How to finish`. It names no logbook tool and no 008 judgment tool.

### R14 · Trace per agent and cost (FR-37, NFR-03, I12)
- Top-level `outcome`, `model_calls`, `tool_calls`, `thinking` stay the coordinator's. `outcome` is `skipped` when the coordinator did not start, including an aborted line whose abort happened in the investigator (the investigator entry carries `aborted:<Class>`); any other abort keeps 007's `aborted:<Class>`. `decision_reason` follows R9.
- New `agents_run`: the agents whose loop started, in order (`investigator`, `coordinator`).
- New `investigator` entry (null when nothing was pending and no cause lookup ran): `trigger` (`review` or `cause_lookup`, R2b; older lines read as `review`), `outcome` (`done`, `fallback:<reason>`, `skipped` when only missing logbooks, `aborted:<Class>`), `logbooks` (task ids), `missing`, `marks` (`{turno_id: mark}`, `{}` on an abort), `proposals` (accepted, full, with ids), `control_errors` (one list per rejected output, kept on an abort), `model_calls`, `tool_calls`, `thinking`, `totals`.
- New `proposals_applied` and `proposals_declined` (accepted ids minus applied).
- `totals` = coordinator + investigator, so it may differ from the top-level `model_calls`. `run_totals` sums both agents and gains `by_agent` = `{investigator, coordinator}` with `runs` (lines whose `agents_run` holds the agent), `model_calls`, `input_tokens`, `output_tokens`, `usd`.
- Lines without the new keys (007/008 files) parse with `investigator` null, empty lists and `agents_run` read as `[coordinator]` when `decision` is `call`, else `[]`.

## Edge cases and assumptions
- **X1** · A coordinator fallback that leaves an accepted proposal unapplied is a failed attempt (Q-53, E24): the logbook is investigated again at the next snapshot, within the cap. When some proposals were already applied before the fallback, the re-run sees their effects in its task; a repeated raise gets the ledger's duplicate refusal and stays declined. When every accepted proposal was applied and the fallback concerns only texts, the logbook is reviewed: nothing is left to judge. A coordinator that ends `done` without applying has declined: the logbook is reviewed (E18).
- **X2** · A `lift` marked `resuelta` on a fragment that reports no resolution passes control; it is judgment, measured by evals (the IF T03 case).
- **X3** · Two `raise` proposals with one scope both pass control; the second `apply_proposal` gets the ledger's duplicate refusal and stays declined.
- **X4** · A v3 file migrated to v4 has no review rows, so its next snapshot's task lists every readable logbook; real runs start fresh.
- **X5** · A given-up logbook stays readable: a later investigator may still read and cite it for a case without a cause.
- **X6** · `apply_proposal` results carry `avisos` but no perspectives; a notice created by a judgment brings its numbers in `borrador`.
- **X7** · An empty logbook file is present: the investigator may read it and return no proposals.
- **X8** · An internal failure inside `apply_proposal` follows 008 R10 (`WritesClosed`, abort before `finish`); 008 E33 is adapted to it.
- **X9** · The 008 judgment tools stay registered in `build_server` (and tested) but are offered to no agent; spec 010's allowlist must exclude them, or `apply_proposal`'s binding to validated ids could be bypassed by a wiring change. `build_server` is not changed here.
