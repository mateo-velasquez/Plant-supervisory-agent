# 004 · Notices and shift reports — Spec

- **Status:** Implemented
- **Requirements:** FR-21, FR-22, FR-23, FR-24, FR-25, FR-26, FR-38 (notice trace), NFR-04, NFR-10
- **Stories:** US-04, US-05
- **Decisions:** ADR-0003 (SQLite registry, single writer), ADR-0008 (unit of work), [ADR-0010](../../docs/adr/0010-notice-outbox-delivery-after-commit.md) (transactional outbox for notice delivery, at-least-once). Q-14 (amended), Q-17 (decided), Q-23 (amended), Q-30 (open, spec 008), Q-31 (decided), Q-32 (decided).
- **Week:** W1

## Goal
Decide in code which notices each snapshot produces (immediate alert, news for the shift report, or silence), build them in the output contract, store every decision in the registry inside the snapshot's transaction, and deliver alerts and shift reports through a pluggable channel only after the commit. This closes the threshold-only system: the full series runs without the model.

## Scope
- **In:**
  - Notice contract: `Notice`, `ActiveCaseRow`, `ShiftReport`, cause and evidence types, deterministic `notice_id`.
  - Pure rules in `cases`: alerts from the last `CaseDelta`, novelty (news) with reasons, the report set, active-case rows, `motivo`/`origen`, the default `no_declarada` cause and its stage (Q-32), Spanish template text, and the per-snapshot decision builder.
  - Registry schema version 2: a `notices` table (decisions plus outbox) and `SqliteNoticeStore` as `registry.notices`; two new reads on `SqliteCaseRepository` (`resolved_unreported()`, `last_deviation_row()`).
  - `Notifier` port with console, file and composite adapters; `Settings.notices_dir`.
  - Runner: an optional post-commit port and `OutboxDispatcher`; `ThresholdPipeline` (the production `SnapshotPipeline`) and its reusable closing glue.
  - Integration tests over a 2-shift synthetic series, including interruption and resume.
- **Out:**
  - Model-written text, cited causes and evidence, raises and lifts (specs 007 and 008). This spec always calls `track` with no raises.
  - Hooks that check the agent against these rules (spec 010); they must reuse `cases/novelty.py`.
  - Output schema validation with retry (spec 011), the CLI and composition root (spec 012), HTML rendering (spec 014).

## Behavior

**Per-snapshot decisions (FR-21, FR-22, FR-24, §4, Q-14 amended)**
- For every case in the last `CaseDelta` of a snapshot, record per-case decisions with the contract's three types:
  - `alerta_inmediata`: the case has an `escalated` event in the delta. Deliverable.
  - `informe_de_turno`: the case is news (novelty rules below) against its last report. At a closing snapshot it is a news item of the report. At a mid snapshot it is recorded as "goes to the report", is not deliverable and nothing is sent.
  - `sin_aviso`: the case is not news (unchanged since its last report). Not deliverable.
- Each evaluated case gets exactly one decision, with one exception: a case that escalates at a closing snapshot gets both its alert and its `informe_de_turno` news entry. A case with an alert never gets `sin_aviso`. At a mid snapshot, an alerted case gets only the alert.
- At a closing snapshot, every case of the report set gets a decision. That adds an `informe_de_turno` (its news entry) for each case resolved earlier in the shift and not yet reported as resolved, although it is not in the delta.
- A mid-snapshot `informe_de_turno` records that the case had changed against its last report at that snapshot. The closing report re-evaluates every case: a change reverted by the close that §4 does not count (a dip, not a peak) is not news there (E17).
- **Source of decisions (Q-27):** notices are built only from the last `CaseDelta` of the snapshot. In this spec `ThresholdPipeline` calls `track` once, with `raises = frozenset()`.

**Immediate alert (FR-21, §4, Q-08)**
- An alert is built for each case with an `escalated` event in the last delta, in the snapshot where it happens, including a case that opens already critical (Q-08).
- `alerted_case_ids(delta)` returns those case IDs in delta event order (for spec 010's hooks); `alerts_for(delta, metrics)` returns the cases themselves and checks that each has metrics.
- At most one per case: the lifecycle never emits a second `escalated` for a case (003), and the notice store rejects a second `alerta_inmediata` for the same `case_id` (backstop).
- An alert always has `estado = escalado` and `severidad = critica`.

**Novelty rules (FR-22, FR-24, §4, Q-26, Q-28)**
- Pure functions in `cases/novelty.py`. They read only the case's baseline fields (`last_reported_at`, `last_reported_state`, `last_reported_severity`, `max_severity_since_report`), never `CaseEvent`s. Events drive alerts only.
- A case is news if and only if at least one reason applies. The reasons, in this order:
  - `new`: `last_reported_at is None`.
  - `resolved`: `state == resuelto` and `last_reported_state != resuelto`.
  - `state_changed`: the case is active, it was reported before, and its normalized state differs from the normalized `last_reported_state`. Normalization maps `abierto` and `en_seguimiento` to the same value (§4).
  - `severity_changed`: it was reported before and `current_severity != last_reported_severity`. A drop to `ninguna` counts (Q-26).
  - `peak`: `max_severity_since_report` is set and greater than `current_severity` (§4: "una severidad más alta que la que tienen al cierre").
- A resolved case already reported as resolved is never news: no reason can apply.
- No repetition: after a case is marked reported, its baseline equals its current values and its max is empty (Q-28), so it is news again only after a new change or a new peak.
- `expected_news(cases)` returns one `NewsItem(case, reasons)` per news case, ordered by `case_order` (`all_combinations()` index, then `opened_at`). `news_reasons(case)` gives the reasons of one case. Spec 010's hooks call these; they never reimplement them.

**Report set (FR-22, §4)**
- `report_set(evaluated, resolved_unreported)` is the pure definition of which cases a closing report covers: the evaluated cases (the last delta's cases: active after `track`, or resolved at this snapshot) plus the given resolved-unreported cases, deduplicated by `case_id` with the evaluated version winning, in `case_order`.
- It raises `ValueError` naming a case of `resolved_unreported` that is not `resuelto` or was already reported as `resuelto`.
- The pipeline passes `resolved_unreported()` as read from the registry, unfiltered (it includes cases resolved at this closing snapshot). The builder, the pipeline and spec 010's hooks all call `report_set`; deduplication happens only there.

**Shift report (FR-22, FR-23, §4)**
- Exactly one `informe_de_turno` report per closing snapshot; none at a mid snapshot.
- **`novedades`:** the `informe_de_turno` notices of the report set's news cases, in `case_order`. They are the same notices stored as per-case decisions at that snapshot.
- **`casos_activos`:** one `ActiveCaseRow` per case active at the close, in `case_order`, with `gap_unidades`, `gap_pct`, `retraso_dias`, `severidad` (current), `severidad_maxima` (max since the previous report), `estado` and `etapa_cuello`, all from the closing snapshot. `etapa_cuello` is the current snapshot's bottleneck (a metric of the current state), not the cause's stage. A resolved case is never in `casos_activos`.
- The report is built from case values **before** marking (FR-23), so `severidad_maxima` is never empty.
- A shift with no cases in the report set still yields a report, with empty `novedades` and `casos_activos`.

**Marking as reported (FR-14, Q-28)**
- At a closing snapshot, after the snapshot's final `track` and after the report is built and saved, `tracker.mark_reported(case_id, snapshot_id)` runs for every case in the report set, and only for them.
- So a case resolved in an earlier shift (already reported as resolved) is never re-marked, and its max is not emptied again. This closes 003's re-marking risk.
- No case is marked at a mid snapshot.

**`motivo` and `origen` (FR-25, Q-13, Q-31)**
- `motivo` is a list ordered `gap`, `retraso`, `bitacora`, with every trigger at the notice's effective severity `E` (the case's current severity):
  - `gap` if the gap severity at this snapshot equals `E`;
  - `retraso` if the delay severity equals `E`;
  - `bitacora` if a raise is in force and the minimum severity is below `critica` (the raise was necessary).
- It is empty when `E` is `ninguna`. With `E` above `ninguna` it is never empty (§2: the minimum is the max of gap and delay severity).
- `origen = agente` if and only if `bitacora` is in `motivo`; otherwise `umbral`.
- Until spec 008 no raise exists, so every notice from the pipeline has `origen = umbral`.

**Cause and evidence (FR-16, FR-18, §6, Q-17, Q-32)**
- Until spec 008, every notice's cause is `no_declarada`, and `evidencia` is empty.
- **Stage (Q-32, decided):** `etapa` is the bottleneck at the case's **last snapshot with a deviation** (minimum severity ≥ `media`), for every notice:
  - an active case with a deviation at this snapshot: this snapshot's bottleneck;
  - an active case without a deviation at this snapshot (clean, Q-26): the bottleneck of its last history row with a deviation;
  - a case resolved earlier in the shift: the same;
  - if that snapshot's bottleneck was `None`, `etapa = null` (Q-17). The search never goes further back.
- The pipeline reads that row with `last_deviation_row(case_id)` after `track`, so for a case with a deviation now it is this snapshot's own row. Every case has one: its opening snapshot has a deviation.
- **Q-17 (decided, option A):** `etapa = null` is never filled with a guess (§6). The text says no bottleneck stage was identified, and says the deviation was gap-only when that is known (see Text).

**Text (`texto`)**
- Plant-facing, in Spanish; code and docs stay in English. Deterministic templates until spec 008 (exact strings in E20–E22).
- **Formatting:**
  - Combination: `<modelo> × <mercado>` with the data values (`Sedán × Local`).
  - Severities: `ninguna`, `media`, `alta`, `crítica`. States: `abierto`, `en seguimiento`, `escalado`, `resuelto`. Stages: their data value (`montaje`).
  - Gap units: rounded to one decimal, halves away from zero, on `Decimal(str(value))`; a trailing `,0` is dropped; decimal comma; the sign is decided after rounding: `−` (U+2212) when negative, `+` when positive, none for zero. Suffix ` u`. Example: `−12 u`, `−2,5 u`, `+6 u`, `0 u`.
  - Gap %: rounded to an integer, halves away from zero; the same sign rules; suffix ` %`. `None` (plan 0, Q-16) is `sin plan en el turno`.
  - Delay, decided on the value rounded to one decimal (the one displayed): `0` → `sin retraso`; `1` → `retraso 1 día`; otherwise `retraso <n> días` with `<n>` rounded to one decimal like units (`retraso 1,5 días`); `None` → `retraso fuera del horizonte de embarques`.
- **Cause sentence:**
  - `etapa` set: `Causa no declarada, etapa <etapa>.`
  - `etapa` null and gap-only known: `Causa no declarada: desvío solo por gap, sin etapa cuello identificada.` Gap-only is known only when the cause's snapshot is this snapshot, and then means gap severity ≥ `media` and delay severity < `media`.
  - `etapa` null otherwise: `Causa no declarada, sin etapa cuello identificada.` History rows do not store gap and delay severities, so an older cause snapshot never gets the gap-only phrase (E22l).
- **`alerta_inmediata`:** `<combinación> escaló a <severidad> en <snapshot_id> por <motivo>: gap <unidades> (<pct>), <retraso>. <causa>` where `<motivo>` joins `gap`, `retraso`, `bitácora` with ` y `.
- **`informe_de_turno` (per case):** `<combinación>: <cambios>. Estado <estado>, severidad <severidad>, máxima <máxima>. <causa>` where `<cambios>` joins, with `; `, one phrase per reason in reason order:
  - `new` → `caso nuevo`;
  - `resolved` → `resuelto en <resolved_at>`;
  - `state_changed` → `estado <estado reportado> → <estado>`;
  - `severity_changed` → `severidad <severidad reportada> → <severidad>`;
  - `peak` → `pico de <máxima>`.
  - For a resolved case, only `resuelto en <resolved_at>` and, when `peak` applies, `pico de <máxima>` are written: resolution implies `ninguna`, so `severidad <x> → ninguna` is omitted. `news_reasons` still returns the full tuple.
- **`sin_aviso`:** `<combinación>: sin cambios desde el informe de <last_reported_at>.`

**Notice contract (FR-25, Q-13, Q-31)**
- `Notice` (frozen) fields: `notice_id`, `snapshot_id`, `case_id`, `modelo`, `mercado`, `tipo`, `severidad` (current), `severidad_maxima` (max since the previous report), `estado`, `origen`, `motivo` (list), `causa {categoria, etapa}`, `evidencia [{bitacora, fragmento}]`, `texto`. JSON keys are exactly these names (ADR-0005).
- Validation (`ValueError`): `notice_id` equals `<snapshot_id>-<tipo>-<case_id>`; `motivo` has no duplicates and follows the order `gap`, `retraso`, `bitacora`; `origen == agente` iff `bitacora in motivo`; `motivo` is empty iff `severidad == ninguna`; `severidad_maxima >= severidad`; `tipo == alerta_inmediata` implies `estado == escalado` and `severidad == critica`.
- A `Notice` is never copied with `model_copy(update=...)`, which skips these validators; a changed notice is built anew.
- `ShiftReport` (frozen) fields: `turno_id`, `snapshot_id`, `novedades [Notice]`, `casos_activos [ActiveCaseRow]`. Validation: every news item has `tipo = informe_de_turno` and the report's `snapshot_id`; `case_id`s are unique within `novedades` and within `casos_activos`.
- **IDs (NFR-04):** a per-case notice's `notice_id` is `<snapshot_id>-<tipo>-<case_id>` (e.g. `S003-alerta_inmediata-S001-Sedán-Local`); the report's is `<turno_id>-informe` (e.g. `T01-informe`). Stable across runs and resumes.
- The contract JSON is what spec 011 validates.

**Notice store and outbox (Q-23 amended, ADR-0010, NFR-10)**
- Registry schema version 2 adds a `notices` table. An existing version 1 file is rejected (003 E21b behavior); the run starts from a fresh file.
- `registry.notices` (`SqliteNoticeStore`) is a collaborator on the registry's shared session, like `registry.cases`.
- Each row has a `kind`: `notice` (a per-case decision, with its `case_id`) or `report` (the shift report, `case_id` NULL, `tipo = informe_de_turno`). A row is **deliverable** when it is a report or an `alerta_inmediata`; deliverability is computed, not stored.
- `save(snapshot_id, decisions, report)`:
  - runs only inside `processing` for `snapshot_id`, through the single write guard (`RuntimeError` outside, `ValueError` naming both ids for another snapshot);
  - requires every decision's and the report's `snapshot_id` to be `snapshot_id` (`ValueError` naming both);
  - replaces the snapshot's set: it deletes the snapshot's rows, then inserts one row per decision and then the report, in that order (`idx`), each with its contract JSON;
  - raises `ValueError` naming the `notice_id` when that ID is already stored by another snapshot;
  - raises `ValueError` naming the case when an `alerta_inmediata` for a `case_id` that already has one is saved (partial unique index; §4 "una por caso");
  - is atomic: a `save` that raises writes nothing.
- Rows written in a unit of work that rolls back do not persist; with the snapshot rolled back, nothing is ever delivered for it.
- `pending()` returns the deliverable, undelivered rows in processing order (`seq`, then `idx`), as `PendingDelivery(notice_id, item)`. It runs only outside `processing` (`RuntimeError` inside, like `record_anomaly`).
- `mark_delivered(notice_id, at)` runs only outside `processing` (`RuntimeError` inside), in its own small transaction. `at` must be timezone-aware (`ValueError` otherwise) and is stored as offset-aware ISO 8601. An unknown `notice_id` raises `ValueError`. Marking an already delivered notice is a no-op that keeps the first time.
- `for_snapshot(snapshot_id)` returns the snapshot's decisions and report in save order (traceability, FR-38).

**Delivery after commit (Q-23 amended, ADR-0010, FR-26)**
- `run_series(..., post_commit=None)` accepts an optional `PostCommit` port. With `None`, behavior is exactly that of specs 002 and 003.
- `post_commit.after_commit()` is called once at the start of the run, **before** the upfront checks, so a run with bad input still delivers notices committed by an earlier run; and once after each committed snapshot. Never for a skipped arrival, never inside `processing`.
- An `Exception` that escapes `after_commit` is logged at ERROR by the runner and the run continues: the snapshot is already committed, so it is never a `RunAborted`. `KeyboardInterrupt` propagates.
- `OutboxDispatcher(notices, notifier, clock)` implements `PostCommit`. Each flush reads `pending()` and, for each item in order, calls `notifier.report` for a `ShiftReport` or `notifier.alert` for a `Notice`, then `mark_delivered(notice_id, clock())`.
- On an `Exception` from the notifier, from `mark_delivered` or from `pending()`, it logs at ERROR (naming the `notice_id` when there is one) and stops the flush, so order is preserved. The item stays pending and is retried at the next flush or the next run. `KeyboardInterrupt` propagates.
- **Guarantee:** no notice is lost and none is sent before its snapshot commits. A notice is re-sent only if the process dies between a successful send and its delivered mark (at-least-once). The file adapter is idempotent by `notice_id`, so the file result is identical.

**Channels (FR-26)**
- `Notifier` port: `alert(notice)` and `report(report)`.
- `FileNotifier(directory)`:
  - Each report goes to `<directory>/informe_<turno_id>.json`: the UTF-8 bytes of its contract JSON, followed by one `\n`.
  - Alerts go to `<directory>/alertas.jsonl`, one contract JSON per line in delivery order, LF line endings, exactly one trailing `\n`. An alert whose `notice_id` is already in the file is skipped; otherwise the whole file is rewritten with the new line.
  - Every write is atomic: a temporary file from `tempfile.mkstemp(dir=directory, suffix=".tmp")`, written as bytes (LF on every OS), closed, then `os.replace`d over the target; on any exception the temporary file is unlinked and the target is unchanged.
  - It creates `directory` if missing. Re-delivering the same report or alert leaves the files byte-identical.
- `ConsoleNotifier(stream)`: writes a human-readable rendering (default `sys.stdout`): an alert line with its `notice_id` and `texto`; a report with its `turno_id`, every news `texto` and every active `case_id`. It never raises on encoding: text is encoded with the stream's encoding and `errors="backslashreplace"` (e.g. `−` on a cp1252 console becomes `−`).
- `CompositeNotifier(notifiers)`: calls each notifier in order; the first exception propagates and the later ones are not called. The dispatcher then retries the whole item, so only durable, idempotent channels may raise inside a composite (the file adapter); the console never raises on encoding.
- `Settings.notices_dir = output_dir / "notices"`, a derived property with no new environment variable.

**`ThresholdPipeline` (ADR-0002, Q-23, Q-27)**
- Implements `SnapshotPipeline`. Inside `processing` it only computes and writes to the database; it never performs external I/O:
  1. `releases.released_so_far()` → `compute_metrics` → `releases.record_releases(snapshot)`;
  2. `tracker.track(snapshot_id, metrics, frozenset())`;
  3. `shift_close(shift, position, reader)`: at a closing snapshot, the shift and the registry's raw `resolved_unreported()`; `None` at a mid snapshot;
  4. `deviation_rows(...)`: the last history row with a deviation for every delta case and every resolved-unreported case (Q-32);
  5. build the per-case decisions and, at a closing snapshot, the report (novelty over values before marking);
  6. `notices.save(...)`, once;
  7. at a closing snapshot, `tracker.mark_reported` for each case in the report set.
- `shift_close` and `deviation_rows` are module-level functions, so spec 008's agent pipeline reuses the closing glue.
- Outside the transaction, only the post-commit dispatcher delivers to notifiers.
- No hook for raises: spec 008 changes the pipeline when it needs them.

**Notation**
- SeL = Sedán × Local, SeE = Sedán × Europa, SL = SUV × Local, PL = Pickup × Local, PB = Pickup × Brasil.
- A case is written `id: state / current / max; reported <state>/<severity> at <snapshot>` ("never reported" when the baseline is `None`). Severities use their data values.
- Facts are `(gap units, gap %, delay days, bottleneck; gap severity, delay severity)` at the case's current snapshot.
- "Cause row" is the row `last_deviation_row` returns (Q-32), written `<snapshot> <bottleneck>`.
- "The registry" is `SqliteRegistry(":memory:")`, or a `tmp_path` file where reopening matters.
- Texts use U+2212 for minus and U+00D7 for ×.

## Edge cases and assumptions
- **Q-08:** a case that opens already critical gets its only alert in the opening snapshot (E6). At a mid snapshot that alert is its only decision.
- **Q-13, Q-31 (decided):** `motivo` lists every trigger at the effective severity; `bitacora` only when the raise was necessary; `origen = agente` iff `bitacora` (E19). Until spec 008 every pipeline notice is `umbral`.
- **Q-14 (amended):** one per-case decision per evaluated case and snapshot, with the closing-escalation exception; `sin_aviso` means only "unchanged since the last report" and serves to audit silences. Noise (FR-39) is measured by comparing consecutive reports (E37, E38, E41).
- **Q-15 (context):** every case crosses a closing snapshot before it can resolve, so every case appears as `new` in exactly one report, and at most one resolved-unreported case per combination exists at a closing snapshot.
- **Q-17 (decided, option A):** a cause snapshot with bottleneck `None` gives `etapa = null`; the text says no stage was identified, and gap-only when that is known (E20, E22d, E22l, E41).
- **Q-23 (amended), ADR-0010:** decisions are stored inside the snapshot's transaction; delivery happens after commit through the outbox; at-least-once with an idempotent file adapter (E43–E45).
- **Q-26:** a drop to `ninguna` is a severity change, hence news (E13).
- **Q-27:** notices come only from the last delta; `ThresholdPipeline` calls `track` once and `save` once (E7).
- **Q-28:** the report reads the max before marking; marking empties it, so a reported peak is never repeated (E14, E40).
- **Q-29 (open, spec 008):** not reachable here (no raises).
- **Q-30 (open, spec 008):** a raise and its lift in the same snapshot. Unaffected here: only the last delta produces notices, so an undone raise yields no alert; a re-`save` in the same unit of work replaces the snapshot's notice set (E26d).
- **Q-32 (decided):** the cause's stage is the bottleneck at the case's last snapshot with a deviation, never further back; `etapa_cuello` in `casos_activos` stays the current bottleneck (E20, E22f, E22i, E41).
- **Assumption, no closing is skipped:** 61 arrivals cover the 60 snapshots, and Q-21/Q-22 stop the run on a missing or unloadable snapshot, so every closing snapshot is processed and every shift gets its report. A resolved case is therefore always reported in the shift where it resolved.
- **Assumption, resolved-case text:** it says the case resolved and adds `pico de <máxima>` only when there was a peak; it omits `severidad <x> → ninguna`. `news_reasons` keeps the full tuple for the hooks (E22k).
- A resolved case can have a peak only through a raise: resolution needs two clean snapshots after the last report, so without a raise its max is `ninguna` (E22k is reachable only from spec 008).
- A mid-snapshot `informe_de_turno` is a statement at that snapshot, not a promise: a dip reverted by the close is not news (E17).
- A case resolved at a closing snapshot is in that report's `novedades` (`resolved`) and not in `casos_activos`.
- A repeated snapshot is skipped before processing, so it produces no notice row and no delivery (FR-02, E41b).
- Every notice from the pipeline has `severidad_maxima` set: each case in a decision was evaluated after its last mark (003 Report baseline).
